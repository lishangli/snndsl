# 为什么需要这个项目

> 结论先说：**它填的是"前端"这个空档，不是一个更好的运行时。**
> SNN 生态在"算子库"和"硬件中间表示"两端都不缺东西，缺的是把人的意图翻译成这两者的那一层。

## 1. 现有生态的三层，以及断在哪

| 层 | 代表 | 解决什么 | 缺什么 |
|---|---|---|---|
| 运行时库 | snnTorch、SpikingJelly、Norse、Lava | 用 Python 写 SNN、跑训练 | 图是动态的，**编译期什么都看不到** |
| 中间表示 | **NIR**（Nature Comm. 2024） | 硬件厂商的通用交换格式，Loihi / SpiNNaker2 / Speck / Xylo 都读 | **没有前端**——谁来生成 NIR？ |
| 前端 / DSL | Sango、cuSpike 的 CSM、本仓库 | 人写的东西 | 都还不成熟 |

断点在第二、三层之间：**NIR 定好了"硬件该收到什么"，但没人管"人怎么写出那个东西"。**

现实后果是同一份网络要写两到三遍：

```
论文里的方程  →  PyTorch/snnTorch 实现（训练）
              →  重写成 NIR 图（部署，手工翻译，容易和训练版不同步）
              →  能耗/稀疏度等训练完跑profiler才知道（无法在选型阶段估算）
```

这三份代码之间没有任何机制保证一致。你在训练版里改了 `tau`，部署版忘了改，烧到板子上才发现——这类问题在 SNN 里比 ANN 更常见，因为 SNN 多了一整个时间维度。

## 2. 这个项目做的是"一次描述，三处产出"

```
                  ┌─→ 可读的 PyTorch 源码  → 训练 / BPTT
  一份描述 ────────┼─→ 静态 SNN IR (JSON)    → 优化 / 成本分析
  (文本 .snn 或   └─→ NIR                  → 神经形态硬件
   Python 嵌入)
```

关键在于中间那层是**静态**的。一旦图在编译期固定，三件事才有可能：

1. **编译期优化**：buffer 复用（实测 −25.3%）、flatten 折进 dense、时间步展开/循环调度（T=8 时代码量 32 层 → 4 层）
2. **编译期成本估算**：fan-in/fan-out 已知，能耗和脉冲预算不用等训练完
3. **硬件导出**：NIR 要求图固定，动态图给不出来

## 3. 双前端不是炫技，是为了承认"两种人都存在"

| | 文本 DSL (`.snn`) | Python 嵌入 |
|---|---|---|
| 适合 | 论文复现、教学、代码审查、非 Python 工具链 | 真实工程、循环/条件、团队协作 |
| 循环生成 N 个 block | 做不到（`pipeline:` 是平铺的） | `for i in range(4): h = ...` |
| IDE 补全 / 调试 | 无 | 免费 |
| 静态可分析 | 强 | 强（构造完就是静态 IR） |

两个前端**产出同一个 IR**，这不是宣传语，是可以测的：

```
op 序列一致 : True
shape 一致  : True
参数量      : 203530 vs 203530
MAC         : 1626112 vs 1626112
生成代码行数: 119 vs 119
```

更强的一条：**checkpoint 跨前端通用**。用 `.snn` 训练出的权重直接加载进 Python 前端编译的模块，`missing=[]`、`unexpected=[]`，全量 10000 张 MNIST 都是 **97.21%**。

这说明抽象没有漏：前端只负责"怎么说"，后端只认 IR。

## 4. 真实价值，按可验证程度排序

### 4.1 编译期挡住 SNN 特有的静默错误（最有价值）

我用等权重的 PyTorch 手写实现做对照，故意犯 4 个新手常见错误，**没有一个会报错**：

| 手写错误 | 后果 | 报错 |
|---|---|---|
| 忘了除以 T | logits 尺度差 8 倍（训练时等效学习率放大 8 倍） | 无 |
| 忘了 `v = v - s*v_th` | 精度反而从 98.3% 涨到 98.7% | 无 |
| 硬阈值代替 surrogate | **前向输出完全相同**，只有梯度为 0 | 无 |
| 状态跨 batch 泄漏 | 静默 | 无 |

第三条是 SNN 独有的：我验证了 `fast_sigmoid` 的前向**严格等于硬阶跃**，只有反向是软的。

```
forward  [0, 0, 0, 0, 1, 1, 1]   ← 和 (x > 0) 一模一样
grad     [0.006, 0.012, 0.04, 1.0, 0.04, 0.012, 0.006]
```

也就是说，写出一个**没有梯度的 SNN**，推理完全正常、精度一分不掉，只有训练时"学不动"。这是最难 debug 的一类 bug。

在 DSL 里这根本不是你能犯的错——你写 `v > v_th`，编译器自己换成 surrogate。同理，`state v = 0.0` 声明后，分配、初始化、跨 batch 重置都是生成的。

### 4.2 能耗结论可以在选型阶段就拿到

我的 MNIST 例子报告 **1.01× 节能**，也就是基本没省。原因不是实现差，而是结构：

```
ANN dense :    1,626,112 MAC                    -> 7480.12 nJ
SNN event :        6,173 AC + 1,605,632 MAC     -> 7391.46 nJ
```

首层 `784→256` 占 98.7% 的 MAC，而它吃的是 rate 编码的**模拟电流**，不是脉冲，必须按 MAC 计费。

编译期就能算出这条敏感性曲线：

| 首层输入发放率 | SNN 能耗 | 相对 dense ANN |
|---|---|---|
| 100%（模拟电流） | 1450.9 nJ | 5.16× |
| 13%（≈MNIST 平均像素强度） | 193.7 nJ | 38.61× |
| 5% | 78.3 nJ | 95.75× |

**"你的 SNN 省不省电,取决于首层能不能吃到稀疏脉冲"** ——这句话在选型阶段就能得出，不用等训练完、不用买板子。这比一个漂亮的倍数有用。

### 4.3 一次描述，部署和训练不会不同步

改 `tau` 只改一处，三处产出一起变。审计也简单：IR 是 JSON，可 diff。

### 4.4 NIR 这条链路是真的通了

`snndsl export` 能导出带权重的 NIR，能被 `nir.read()` 读回，节点映射到 `Affine`/`LIF`/`Conv2d`/`Flatten` 等原语。这意味着这个前端接上了 Loihi / SpiNNaker2 / Speck / Xylo 的生态，而不是又一个孤岛。

## 5. 它不解决什么（这些必须讲清）

- **不是运行时，不是硬件 SDK**。它生成代码和 IR，不负责跑得快。
- **不支持循环突触**，所以做不了 recurrent SNN（EventProp 那一类）。时间维度上的状态只能放在神经元的 `state` 里，不能放在图的边上。
- **不追求 SOTA 精度**。MNIST 97.21% 是没调参的 baseline，加 BN 折叠、更多 epoch、direct coding 应该还能涨。
- **int8 是 weight-only fake quant**，没有生成量化 kernel，实际加速取决于部署框架。
- **硬件链路止步于 NIR 导出，没上真机验证**。
- **性能不如手写 PyTorch**。生成的代码是标准 PyTorch（我验证过和手写版逐位一致），但 PyTorch 生态的算子融合、显存优化都比这里成熟。

## 6. 所以它的意义在哪

如果只要"写 SNN 方便"，用 snnTorch，别用这个——它的生态、文档、预训练模型都更好，门槛也更低。

这个项目成立的前提是：**你同时需要训练和部署，并且希望这两件事不脱节。** 在这个前提下：

- 运行时库给不了你静态图和硬件导出
- NIR 给不了你前端
- 硬件厂商的 SDK 给不了你 PyTorch 训练

三者交集就是这块地方。它不大，但是空的。

## 7. 如果要继续做，优先级

1. **验证 NIR 在真机/仿真器上跑通**（Lava 或 pyNIR 仿真）。现在只验证了"能导出、能读回"，没验证"行为一致"。这是最大的未证明项。
2. **补循环突触**。这是表达力的硬边界，挡住了整整一类 SNN 论文。
3. **BN 折叠 + 更好的初始化**，把 MNIST 推到 98%+，证明精度不是瓶颈。
4. **量化到真正的 int8 kernel**，否则"高效推理"始终差一步。

这四件事都不影响现有架构——因为 IR 是对的，缺的是后端和 pass。
